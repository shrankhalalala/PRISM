# Dataset and Preprocessing: Phases 1–2

## 1. Dataset role

The Phase 1 dataset exists to validate ingestion, schema enforcement, API behavior,
and dashboard visualization. It is not a model-training dataset and is not evidence
about the behavior of the Delhi or Indian power grid.

Two independent artifacts are included:

| Artifact | Location | Purpose |
|---|---|---|
| Synthetic hourly measurements | `data/raw/synthetic_measurements.csv` | Exercise time-series validation and presentation |
| Synthetic grid topology | `data/raw/grid.json` | Exercise topology validation, persistence, API, and dashboard behavior |

The processed measurement file and its audit are stored in `data/processed/`.

## 2. Provenance and generation

The measurement fixture is generated by `scripts/generate_sample.py` using Python's
pseudorandom generator with seed 42. It contains 336 consecutive hourly records
from 2026-01-01 00:00 UTC through 2026-01-14 23:00 UTC. Demand and renewable values
are deterministic combinations of periodic functions and bounded random variation.
The `source` field is `synthetic_seed_42` for every row.

The topology is also created by the sample-generation script. It is a fictional,
Delhi-inspired teaching network with four generation categories: coal, gas, solar,
and wind import. Asset names, capacities, locations, and connections are not a
digitized representation of the Delhi grid.

The time series and static topology are not synchronized. Their values must not be
joined as though they describe the same instant or physical system.

## 3. Measurement schema

| Field | Type | Unit | Definition and validation |
|---|---|---|---|
| `timestamp` | ISO 8601 string | UTC | Explicit `Z` or numeric offset required; normalized to UTC; must lie on an hourly boundary and be unique |
| `demand_mw` | float | MW | Aggregate synthetic demand; finite and nonnegative |
| `solar_mw` | float | MW | Aggregate synthetic solar output; finite and nonnegative |
| `wind_mw` | float | MW | Aggregate synthetic wind output; finite and nonnegative |
| `frequency_hz` | float | Hz | Synthetic frequency; finite and inside the 45–55 ingestion sanity range |
| `source` | string | none | Required provenance label |
| `quality_flag` | derived string | none | Set to `validated` after the declared checks pass |

`validated` means only that the row passed Phase 1 input checks. It does not confirm
measurement accuracy, authenticity, sensor calibration, or operational fitness.

## 4. Preprocessing procedure

The pipeline performs these operations in order:

1. Confirm that every required input column exists.
2. Retain the canonical fields and reset the row index.
3. Verify that each timestamp declares a timezone, then parse it as UTC.
4. Convert measurement columns to numeric types.
5. Construct Boolean rejection reasons for timestamp, numeric, sign, frequency,
   provenance, and duplicate checks.
6. Reject a row if any reason is true. Rejection reasons can overlap, so their sum
   may exceed the number of rejected rows.
7. Sort accepted rows by timestamp.
8. Compare adjacent accepted timestamps and record missing hourly periods.
9. Write timestamps in canonical `YYYY-MM-DDTHH:MM:SSZ` format.
10. Add `quality_flag=validated` and write the cleaned CSV and JSON audit.

The pipeline performs no interpolation, forward filling, resampling, normalization,
or outlier replacement. All rows in a duplicate timestamp group are rejected.

## 6. Candidate real-data sources

The initial source assessment identifies Delhi SLDC Grid Watch for possible demand
and frequency observations, Ember for historical electricity context, NITI Aayog
ICED for plant metadata, and CEA power maps for topology reference. Phase 1 has not
imported data from these sources or confirmed that they provide compatible hourly,
Delhi-level coverage under suitable reuse terms.

Before a source is accepted, the team must record:

- publisher and download URL or API version;
- licence and permitted research use;
- geographic boundary and aggregation method;
- timestamp semantics, timezone, cadence, and publication delay;
- units and measurement definitions;
- coverage period and missingness;
- revisions or corrections by the publisher; and
- a checksum for the exact raw file used in an experiment.

Transmission topology additionally requires verified identifiers, connectivity,
ratings, and electrical parameters before it can support power-flow analysis.

## 7. Requirements for Phase 2 modelling

The modelling dataset must use chronological train, validation, and test periods.
All learned preprocessing parameters, including scalers, must be fitted on training
data only. Forecast target windows may not cross split boundaries. Hyperparameters
must be selected without inspecting the test period.

Percentage errors require special treatment when actual solar or wind output is
zero. MAE and RMSE should always accompany any percentage metric, and the chosen
zero-denominator policy must be stated before results are calculated.

Synthetic augmentation, interpolation, or merging across sources must preserve a
column-level provenance record and be evaluated separately from unmodified real
observations.

## 8. Reproduction commands

From the repository root:

```bash
python -m scripts.generate_sample
python -m scripts.prepare_data
```

To validate another CSV against the Phase 1 contract:

```bash
python -m scripts.prepare_data \
  --input path/to/input.csv \
  --output path/to/clean.csv \
  --audit path/to/audit.json
```

Running sample generation intentionally reproduces the committed deterministic
fixtures. External data should be stored and versioned according to its licence and
must not overwrite the synthetic reference without a recorded decision.

## 9. Phase 2 simulation profile adapter

Phase 2 reads the canonical hourly CSV without changing it. For a one-day episode,
`quarter_hour_profile` selects the most recent 24 rows and linearly interpolates
demand, solar, and wind at 15-minute boundaries. Each pair of hourly observations
therefore yields the original value plus values at 25%, 50%, and 75% of the change.
The final observation is held for three additional quarter-hours because no later
hour exists.

This derived profile has 96 points and is used only by the synthetic simulator.
The choice may smooth rapid ramps and does not reconstruct real sub-hourly
variability. Experiments must identify the adapter and retain the source rows;
results created from it cannot be described as measurements at 15-minute cadence.

The first forecasting evaluation uses rows 1–288 for training and the final 48 rows
for testing. It performs no random shuffle. This split validates the experiment
path but remains too short and too synthetic for a general performance claim.

## 10. Phase 2 modelling fixture

Phase 2 extends the same deterministic generator to 2,160 consecutive hourly rows
from 2026-01-01 00:00 through 2026-03-31 23:00 UTC. Daily demand and solar cycles
are supplemented with generated weekly and 90-day demand terms and a slower wind
term. Seed 42 and source label `synthetic_seed_42` remain unchanged. The audit
accepts all 2,160 rows with zero rejected rows, detected gaps, or imputations.

The fixed chronological split contains 1,512 training rows, 324 validation rows,
and 324 untouched test rows. LSTM mean and scale are fitted only on training data.
Evaluation is one-step walk-forward: after each prediction, the actual observation
joins the history for the next prediction. The CSV checksum is retained in
`reports/phase2_forecasting.json`.

This larger fixture is still generated data. It permits executable comparison and
reproducibility checks but does not represent seasonal coverage, real weather,
sensor error, or Delhi grid operation. Phase 3 must acquire and audit a permitted
external or live source before any real-grid forecasting claim.
